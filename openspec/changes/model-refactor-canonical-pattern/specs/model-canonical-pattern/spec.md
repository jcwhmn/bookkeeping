## ADDED Requirements

### Requirement: Entity has no public setters
The system SHALL NOT use public setters on any JPA entity that extends `BaseEntity`. All field updates SHALL go through `toBuilder()`-based immutable updates.

#### Scenario: Entity is created via builder
- **WHEN** a service constructs a new entity
- **THEN** it SHALL use the entity's builder (e.g., `Category.builder().name("x")...build()`)
- **AND** it SHALL NOT call any setter on the entity

#### Scenario: Entity is updated via applyUpdate
- **WHEN** a service updates an existing entity
- **THEN** it SHALL use `existing.applyUpdate(c -> c.toBuilder()...build())`
- **AND** it SHALL NOT call any setter on the entity

#### Scenario: Entity has no @Setter annotation
- **WHEN** a developer inspects the entity class
- **THEN** it SHALL NOT have `@Setter` or `@Data` annotations

---

### Requirement: Service uses applyUpdate for entity updates
The system SHALL use `BaseEntity.applyUpdate(Function)` to update entities in service layer. The function SHALL receive the entity and use `toBuilder()` to apply changes, then call `build()`. The result SHALL preserve the original `id` and `createdAt`.

#### Scenario: Update preserves id
- **WHEN** a service calls `existing.applyUpdate(c -> c.toBuilder().name("new").build())`
- **THEN** the resulting entity SHALL have the same `id` as `existing`
- **AND** Hibernate SHALL execute an UPDATE statement, not an INSERT

#### Scenario: Update preserves createdAt
- **WHEN** a service calls `applyUpdate` on an entity
- **THEN** the resulting entity SHALL have the same `createdAt` timestamp as the source

#### Scenario: Save after applyUpdate does not create duplicates
- **WHEN** a service calls `save()` after `applyUpdate()`
- **THEN** the database row count for that entity SHALL remain unchanged
- **AND** the entity's `sortOrder`/`name`/etc. SHALL reflect the new value

---

### Requirement: Controller is RESTful
The system SHALL use RESTful endpoint design for all entity controllers. Endpoints SHALL NOT use `.json` suffix. Endpoints SHALL use proper HTTP verbs (GET/POST/PUT/PATCH/DELETE). Endpoints SHALL use plural noun in the path.

#### Scenario: List endpoint uses GET on collection
- **WHEN** the frontend requests a list of entities
- **THEN** the controller SHALL expose `GET /api/v1/<plural>` (e.g., `GET /api/v1/categories`)

#### Scenario: Create endpoint uses POST on collection
- **WHEN** the frontend creates a new entity
- **THEN** the controller SHALL expose `POST /api/v1/<plural>` and return 201 Created

#### Scenario: Get single uses GET on resource
- **WHEN** the frontend fetches a single entity
- **THEN** the controller SHALL expose `GET /api/v1/<plural>/{id}`

#### Scenario: Update uses PUT on resource
- **WHEN** the frontend updates an entity
- **THEN** the controller SHALL expose `PUT /api/v1/<plural>/{id}`

#### Scenario: Partial state change uses PATCH
- **WHEN** the frontend toggles a boolean state (e.g., hidden)
- **THEN** the controller SHALL expose `PATCH /api/v1/<plural>/{id}/<state>` (e.g., `PATCH /api/v1/categories/{id}/hidden`)

#### Scenario: No legacy .json endpoints
- **WHEN** a developer inspects the controller
- **THEN** no endpoint path SHALL end with `.json`

---

### Requirement: Controller uses @RequiredArgsConstructor
The system SHALL use Lombok's `@RequiredArgsConstructor` for controller dependency injection. Controllers SHALL NOT have manually-written constructors.

#### Scenario: Controller has @RequiredArgsConstructor
- **WHEN** a developer inspects the controller class
- **THEN** the class SHALL be annotated with `@RequiredArgsConstructor`
- **AND** it SHALL NOT have a manually-written constructor

#### Scenario: Dependencies are final fields
- **WHEN** a developer inspects the controller fields
- **THEN** service dependencies SHALL be `private final` fields

---

### Requirement: DTO uses @MapperAuto
The system SHALL use MapStructPlus `@MapperAuto` annotation on every response DTO record. The annotation SHALL specify `sourceEntity` and `direction = Direction.From`.

#### Scenario: DTO record is annotated
- **WHEN** a developer inspects a response DTO
- **THEN** it SHALL be a `record`
- **AND** it SHALL have `@MapperAuto(sourceEntity = Xxx.class, direction = Direction.From)`

#### Scenario: XxxDtoMapperConverter is auto-generated
- **WHEN** the project is built
- **THEN** `XxxDtoMapperConverter` SHALL be generated in the same package
- **AND** it SHALL be annotated with `@Component` for Spring DI

---

### Requirement: Service uses real mapper in unit tests
The system SHALL use the real `XxxDtoMapperConverter` (auto-generated by MapStructPlus) in service unit tests, NOT a mock. This verifies the auto-generated mapping logic and catches mapping bugs.

#### Scenario: Unit test instantiates real converter
- **WHEN** a developer writes a service unit test
- **THEN** the test SHALL instantiate `new XxxDtoMapperConverter()` (or use a `@BeforeEach` field)
- **AND** the test SHALL NOT use `@Mock` on the mapper

#### Scenario: Unit test verifies field mapping
- **WHEN** the service returns a DTO
- **THEN** the test SHALL assert on DTO field values that came from the entity

---

### Requirement: Integration tests use Apache HttpClient5
The system SHALL use Apache HttpClient5 as the `RestTemplate` request factory in integration tests. This is required for PATCH method support, because JDK's `HttpURLConnection` does not support PATCH.

#### Scenario: RestTemplate uses HttpComponentsClientHttpRequestFactory
- **WHEN** a developer writes an integration test
- **THEN** the `RestTemplate` SHALL be constructed with `new HttpComponentsClientHttpRequestFactory()`

#### Scenario: build.gradle.kts includes httpclient5
- **WHEN** a developer inspects `backend/build.gradle.kts`
- **THEN** the file SHALL include `integrationTestImplementation("org.apache.httpcomponents.client5:httpclient5")`

#### Scenario: PATCH tests are enabled
- **WHEN** integration tests for hide/unhide/partial state endpoints run
- **THEN** they SHALL NOT be marked `@Disabled`
- **AND** they SHALL pass

---

### Requirement: Update path does not create duplicates (regression test)
The system SHALL verify via integration test that the `applyUpdate()` pattern does not create duplicate rows. For every entity that has an update or reorder operation, an integration test SHALL count entities before and after the operation, and assert the count is unchanged.

#### Scenario: Update preserves entity count
- **WHEN** an integration test calls an update endpoint (PUT, PATCH, or reorder)
- **THEN** the entity count before and after SHALL be equal
- **AND** the test SHALL fail if the count increases

#### Scenario: Reorder preserves entity count
- **WHEN** an integration test calls a reorder endpoint
- **THEN** the entity count before and after SHALL be equal
- **AND** the test SHALL fail if the count increases

---

### Requirement: Per-user authorization
The system SHALL filter all entity operations by the current authenticated user. Services SHALL use `securityUtils.requireCurrentUser()` to get the current user ID, and repositories SHALL use per-user query methods (e.g., `findByIdAndUserId`, `findByUserIdAnd...`).

#### Scenario: Service gets current user
- **WHEN** any entity operation runs
- **THEN** the service SHALL call `securityUtils.requireCurrentUser().getId()` to get the user ID
- **AND** the service SHALL pass that ID to the repository query

#### Scenario: Repository uses per-user query
- **WHEN** a service needs to fetch an entity
- **THEN** it SHALL use a per-user query method (e.g., `findByIdAndUserId(id, userId)`)
- **AND** it SHALL NOT use the global `findById(id)` method

#### Scenario: DataInitializer uses per-user check
- **WHEN** the DataInitializer seeds demo data
- **THEN** it SHALL check existence per user (e.g., `findByUserIdOrderBySortOrderAsc(demoUser.getId()).size() > 0`)
- **AND** it SHALL NOT use global `count()` checks

---

### Requirement: Frontend uses correct envelope unwrapping
The system SHALL use the `useApi` composable which already unwraps the `ApiResponse` envelope. Frontend code SHALL NOT double-unwrap the response by accessing `res.result` on an already-unwrapped value.

#### Scenario: Frontend uses unwrapped result
- **WHEN** the frontend calls `api.get<T[]>(path)`
- **THEN** the returned value SHALL be the array directly, not wrapped in `{ result: T[] }`
- **AND** the frontend SHALL assign `data.value = res` (not `data.value = res.result`)

#### Scenario: useApi composable unwraps envelope
- **WHEN** the `useApi` composable receives a response with `{ success, result, errorCode, errorMessage }`
- **THEN** it SHALL return `result` (the unwrapped data)
- **AND** it SHALL throw if `success` is false

---

### Requirement: Frontend uses RESTful paths
The system SHALL update all frontend pages to use RESTful API paths matching the new backend endpoints. Frontend code SHALL NOT call legacy `.json` endpoints.

#### Scenario: Frontend page calls RESTful endpoint
- **WHEN** a frontend page calls the backend API
- **THEN** the path SHALL be `/api/v1/<plural>` (no `.json` suffix)
- **AND** the HTTP method SHALL match the backend endpoint

#### Scenario: Frontend uses PATCH for partial state
- **WHEN** a frontend page toggles a boolean state (e.g., hidden)
- **THEN** it SHALL use `api.patch('/api/v1/<plural>/{id}/<state>', { <state>: value })`
- **AND** it SHALL NOT use `api.put` for partial changes
